# Deconstruct Workflow

Use this workflow to reduce a problem into facts, constraints, mechanics, and causal structure.

## When to use

Use this workflow when:

- the issue is being treated as a black box
- a decision depends on understanding the real mechanism
- cost, complexity, or slowness is being accepted without decomposition
- the current explanation is narrative-heavy and structure-light
- the problem needs to be broken into parts before judging options

## Core question

What is the problem actually made of?

## Process

### Step 1: State the real goal

Write the actual outcome that matters.

### Step 2: Break the issue into components

Reduce the problem into components such as:

- users or actors
- tasks or steps
- costs
- dependencies
- decisions
- risks
- constraints

### Step 3: Identify basic facts

List only what is currently supported by evidence, logic, or hard boundaries.

### Step 4: Separate hard and soft constraints

Classify constraints into:

- hard constraints
- soft constraints
- open assumptions

### Step 5: Map causal structure

Explain what seems to be causing what.

### Step 6: Identify false complexity in the current framing

Show where the issue is being misdescribed as more mysterious than its actual structure.

## Handoff rule

Stop once facts, constraints, components, and causal structure are explicit enough to compare options. If the decomposition already points clearly toward one move, hand off directly to `workflows/decide.md`. If too many options or moving parts remain, move to `workflows/simplify.md`

## Output format

- real goal
- components
- decision-relevant facts
- hard constraints
- soft constraints when relevant
- causal structure
- false complexity in framing
- recommendation when the structure already points one way
- next move

## Quality bar

A good deconstruction should make the issue more concrete, more measurable, and less narrative-driven. If the answer could have been written without naming components or causal structure, the deconstruction is probably still too abstract. It does not need a final decision yet, but it should make the next decision, working recommendation, or next check more obvious.
